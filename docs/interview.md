# 履歷與面試

## 履歷條目

以 PostgreSQL 建立三組公開 Job Shop 基準資料的關聯模型，透過 CTE、JOIN、視窗函數及 VIEW 完成 12 項排程與產能查詢。用 R 實作 FIFO、SPT、LPT 事件派工並驗證九個情境，將 SQL 結果串接 Shiny 甘特圖及互動比較。ft10 基準下，SPT 的完工跨度較 FIFO 短 9.29%。

## 60 秒說明

我想回答同一批工件在不同派工規則下，完工跨度與機台空檔會怎麼變。我使用三組公開 Job Shop 基準，在 PostgreSQL 用案例 ID 和工序 ID 建立複合鍵，再用 R 模擬 FIFO、SPT、LPT。每次完工事件會釋放機台與下一道工序，我用 R 和 SQL 檢查先後順序、加工時間及機台有無重疊。ft10 的 SPT 將完工跨度從 1,184 降到 1,074，但 ft06 的 SPT 反而從 65 增到 88。這個反轉讓我能說明為什麼選派工規則要先分案例測試。面試官可以在 Shiny 切換規則、追到甘特圖上的工序，再看高負荷機台的空檔落在哪裡。

## 常見問答

- **利用率為何會變？** 加工量固定，完工跨度改變了各台機台可用時間的分母。
- **如何證明沒有重疊？** 按情境、機台和開工排序，用 LAG 取得前一道完工，找出當前開工早於前一道完工的記錄。等於前一道完工時點合法。
- **如何找高負荷機台？** 聚合固定加工量後，用 DENSE_RANK 在案例內保留並列最高者。再比較機台空檔與工件等待，作為瓶頸診斷的起點。
- **三規則如何確定先後？** 只排序當下已就緒且機台可用的工序。相同優先值依就緒時間及原始 ID 取得確定性。
- **如何更新展示資料？** 先重跑 R 和 PostgreSQL，通過品質與交叉檢查後重新同步 CSV 並部署。面試頁使用版本化的結果快照。
